# Архитектура Jarvis

Система состоит из одинаковых агентов, общей шины событий, реестра actions и
пользовательских модулей. Main — это только основной экземпляр агента, с
которым обычно говорит пользователь. Tool calling не используется.

## Агенты и сообщения

У каждого экземпляра есть собственные имя, `agent_id`, очередь событий,
история и поток модельного цикла. `agent_id` — внутренний адрес экземпляра,
`name` — читаемое имя. Контексты агентов не пересекаются.

Пресет — готовая неизменяемая конфигурация: системный промпт, доступные модули,
описания и actions со схемами. `agent.spawn` создаёт экземпляр выбранного
пресета и ничего ему дополнительно не передаёт. После получения `agent_id`
родитель отправляет задачу отдельным `agent.message`. Задача не является
отдельным типом `agent.task`. Родитель продолжает работу сразу и не ждёт
дочерний экземпляр.

Сообщение любого агента любому другому агенту — такое же обычное событие, как
событие устройства или результат действия:

```json
{
  "type": "message",
  "data": {
    "from": "agent-0001",
    "text": "Какой движок использовать?"
  }
}
```

Адресат хранится во внутреннем конверте события и не является частью
универсального `data` сообщения. Сообщение всегда встаёт в очередь адресата.
Специального канала для вопросов и завершения нет. Если агент закончил работу,
он отправляет обычное сообщение, а получатель сам решает, что делать дальше.

Права агента определяются выбранным пресетом и не передаются отдельно при
создании экземпляра. Жёсткого правила «субагент может общаться только с
родителем» нет: это определяется actions выбранного пресета.

## Модельный цикл

Каждый цикл имеет следующий вид:

```text
очередь событий агента
        ↓
пачка накопленных событий
        ↓
одно обращение к модели
        ↓
строгий JSON {"actions": [...]}
        ↓
параллельное выполнение actions
        ↓
отдельный action_result для каждого action
        ↓
возврат результатов в очередь
```

Одно событие всегда занимает одно сообщение `user`. Если агент занят моделью
или actions, новые события ждут. Когда агент освобождается, все накопленные
события добавляются в контекст отдельными сообщениями одной пачкой.

Независимые actions из одного ответа запускаются параллельно. Результаты могут
прийти в любом порядке. Действие, зависящее от результата другого, модель
выдаёт следующим ответом после получения соответствующего `action_result`.

Ответ модели имеет только такой контракт:

```json
{
  "actions": [
    {"type": "telegram.send_message", "data": {"chat_id": 482731905, "text": "Да."}}
  ]
}
```

`no_action` — единственное действие ответа, означающее ожидание новых событий.
Иногда локальные structured-output backend добавляют `no_action` к полезному
действию; runtime удаляет из такого ответа лишний `no_action`, чтобы полезное
действие не потерялось.

## Системное сообщение модели

Итоговое поле `system` строится одинаково для всех агентов:

```text
неизменяемый системный промпт пресета
        ↓
доступные модальности модели
        ↓
системное описание event-action и agent loop
        ↓
JSON-каталог доступных actions
```

Для main системный промпт находится в `person_prompt.txt`. Этот файл описывает
только личность, философию и манеру общения цифрового ассистента.

Для обычного агента системный промпт находится в выбранном пресете. Для
встроенного пресета управления модулями он захардкожен в исходниках.

Системное описание event-action и agent loop одинаково для всех агентов. В нём
описаны структура событий, очередь, параллельность, сообщения и строгий JSON.
Личность и художественные инструкции в этот блок не входят.

Tool calling отсутствует. Семантическое описание action находится в
JSON-каталоге, который добавляется в system-сообщение:

```json
{
  "type": "speech",
  "description": "Произнести прямую речь из text. Допустимы [теги] интонации.",
  "data_schema": {
    "type": "object",
    "properties": {"text": {"type": "string"}},
    "required": ["text"],
    "additionalProperties": false
  }
}
```

`response_format` с `json_schema` только ограничивает форму ответа модели.
Отдельных tool-сообщений и роли `tool` нет.

## Модули

Пользовательские модули находятся непосредственно в:

```text
.assistant/
├── agents/
│   └── presets.json
└── modules/
    ├── telegram/
    │   ├── module.json
    │   ├── module.py
    │   ├── actions/
    │   └── handlers/
    └── vacuum/
        ├── module.json
        ├── module.py
        ├── actions/
        └── handlers/
```

Название каталога — `module_id`. Внутри каждого модуля обязательны
`module.json`, `module.py`, `actions/` и `handlers/`. Модуль может объявлять
только actions, только handlers или оба вида.

`module.json` имеет форму:

```json
{
  "name": "telegram",
  "description": "Интеграция с Telegram",
  "entrypoint": "module.py",
  "factory": "create_module"
}
```

`entrypoint` показывает загрузчику, из какого файла брать код. `factory` — имя
функции в этом файле, которая возвращает объект `Module`:

```python
def create_module():
    return Module(
        name="telegram",
        description="Интеграция с Telegram",
        actions=(...),
        handlers=(...),
    )
```

Поля `name` и `description` в объекте `Module` должны совпадать с manifest.
Поля `version` у модуля нет.

Actions и events модуля используют имена с префиксом модуля:

```text
telegram.new_message
telegram.send_message
vacuum.finished
```

Доступ к actions определяется конфигурацией агента. Один модуль может быть
выдан main и любому количеству субагентов.

## Пресет управления модулями

`module_manager` — встроенный пресет, захардкоженный в коде. В
`.assistant/modules/` его каталога нет. Его системный промпт, набор actions и
инструкция работы с файлами заданы в исходниках. Пресет нельзя удалить.

Экземпляр этого пресета работает со всей `.assistant/modules/`, может создавать, изменять, читать,
удалять и проверять любые модули. При создании action он обязан записать его
назначение и строгую JSON Schema в коде модуля. После применения модуля его
actions и handlers сразу регистрируются в runtime.

Основные actions пресета:

```text
workspace.list
workspace.read
workspace.write
workspace.delete
process.run
module.validate
module.complete
agent.message
no_action
```

`module.complete` применяет подготовленный модуль. После этого экземпляр
отправляет родителю обычное событие `message`; отдельного события завершения
работы нет.

## Мультимодальность

Модуль получает внешние данные самостоятельно. Если это изображение, он
скачивает файл, определяет MIME и подготавливает base64 через API:

```python
photo = input_part("image", "image/jpeg", base64_photo)
ctx.emit(
    "telegram.new_message",
    {"chat_id": 482731905, "text": "Что на фотографии?"},
    parts=(photo,),
)
```

`input_part` не создаёт отдельное событие. Это мультимодальная часть того же
события. Ядро проверяет возможности выбранной модели и переводит часть в
формат провайдера. `file` ядро не разбирает: это ответственность модуля.

## Речь

Action `speech` получает прямой текст реплики. В нём допустимы `[теги]`
интонации. Модель не знает о Fish Audio, HTTP, PCM или `ffplay`.

Текст передаётся в TTS worker. Пока идёт синтез и воспроизведение, агент занят,
а новые события копятся в его очереди. Перед запуском `ffplay` worker сначала
накапливает небольшой запас первого PCM-потока, чтобы скорость воспроизведения
не опережала генерацию.

При начале новой речи VAD немедленно прерывает TTS. Результат прерванного
speech action также становится событием и попадает в общую пачку вместе с новой
речью и сообщениями агентов.

## Runtime-файлы

`.assistant/agents/presets.json` хранит сохраняемые пресеты: их имя, описание,
системный промпт и список доступных actions. Живые экземпляры,
истории и очереди существуют только в памяти и исчезают после перезапуска.
