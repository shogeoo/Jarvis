# Архитектура Jarvis

## Граница ядра

Ядро содержит только универсальные механизмы:

- строгий формат событий и действий;
- независимый цикл каждого агента;
- пачки и временной порядок событий;
- проверку structured input и structured output;
- последовательное исполнение actions;
- адресную и широковещательную доставку;
- реестры и загрузку модулей;
- сборку systemprompt;
- жизненный цикл потоков и дочерних процессов.

В ядре зарезервированы только `no_action` и `structure_error`. Остальные типы,
включая результаты действий, принадлежат модулям.

Исходники разделены по ответственности:

```text
jarvis/core/             протокол и цикл агентов
jarvis/modules/          публичный API и загрузчик модулей
jarvis/presets/          файловое хранение пресетов
jarvis/infrastructure/   конфигурация и внешнее модельное API
jarvis/application.py    composition root
```

Изменяемая конфигурация и способности отделены от Python-пакета:

```text
.jarvis/
├── environment.txt
├── modules/
│   └── <module_id>/
│       ├── module.json
│       ├── module.py
│       ├── actions/
│       └── handlers/
├── presets/
│   └── <preset>/
│       ├── personprompt.txt
│       ├── modules.json
│       └── preset.json       # необязательная политика защиты
└── runtime/
```

## Цикл агента

Каждый экземпляр имеет `agent_id`, имя, preset, собственные историю, очередь,
состояние и поток. ID создаётся случайно в диапазоне `agent-000` — `agent-999`
с проверкой занятости.

Цикл выглядит так:

```text
ожидание первого события
        ↓
извлечение всей накопленной пачки
        ↓
добавление каждого события отдельным user message
        ↓
один запрос к модели
        ↓
проверка строгого JSON
        ↓
последовательное исполнение всего массива actions
        ↓
освобождение агента
        ↓
следующая накопленная пачка
```

Агент считается занятым от начала модельного запроса до завершения последнего
action. События, появившиеся в это время, попадают в его FIFO-очередь. Время
возникновения определяет порядок независимо от источника: внешнее событие,
межагентное сообщение и результат action равноправны.

Actions одного ответа исполняются сверху вниз. Исключение в одном action
фиксируется диагностикой ядра, но не останавливает последующие actions. Код
модуля обязан самостоятельно опубликовать событие успеха или ошибки, если
модели нужна обратная связь.

Если action ничего не публикует, после массива агент переходит в ожидание. Это
нормальное и намеренное поведение.

## Исправление структуры

Модельный ответ сначала сохраняется в истории как сообщение `assistant`, затем
проверяется. Ошибкой считается:

- невалидный JSON;
- неверная оболочка `actions`;
- неизвестный или недоступный action;
- аргументы, не соответствующие схеме;
- `no_action` вместе с другими actions;
- отказ модели вместо структурированного ответа.

При ошибке ядро непосредственно добавляет:

```json
{
  "type": "structure_error",
  "data": {
    "code": "invalid_structure",
    "message": "описание нарушения",
    "response": "исходный ответ"
  }
}
```

Агент остаётся занят. Новые внешние события остаются в очереди и не попадают в
контекст исправления. Модель получает повторный запрос с тем же контрактом.
Цикл продолжается до корректного ответа, после чего выполняются исправленные
actions. Только затем агент принимает накопленную внешнюю пачку.

## Доставка событий

`Event` содержит model-visible поля `type` и `data`, а также внутренние поля
маршрутизации. Они не показываются модели.

`ModuleContext.emit()` используется фоновым handler. Без `target` событие
рассылается всем активным агентам, чей текущий `modules.json` содержит
`module_id` источника.

`ActionContext.emit()` используется action. Без явно указанного `target`
событие направляется вызвавшему агенту. Поэтому результат действия не попадает
другим экземплярам даже при общем модуле.

Адресное межагентное сообщение реализовано модулем `agents`: отправка является
action отправителя, получение — обычным event адресата.

## Модуль

Manifest задаёт имя, описание, entrypoint и factory:

```json
{
  "module_id": "telegram",
  "description": "Интеграция с Telegram",
  "entrypoint": "module.py",
  "factory": "create_module"
}
```

Factory возвращает `Module` с actions, самостоятельными events, handlers и
необязательным ранним `prepare(config)`. Prepare выполняется загрузчиком до
запуска агентов; например, `speech_input` на этом этапе подготавливает CUDA без
знаний об этом в bootstrap или ядре.
Handler также перечисляет публикуемые им events. Имена обязаны начинаться с
`module_id.`. JSON Schema проверяются при загрузке.

Все handlers всех установленных модулей запускаются при запуске Jarvis. Наличие
модуля в пресете управляет доставкой событий и доступом к actions, а не запуском
handler.

При горячем обновлении загрузчик ждёт завершения уже исполняемых actions этого
модуля. Начатый цикл использует снимок старого контракта. Следующий цикл читает
новую декларацию и заменяет только system message; история сохраняется.

Модуль, на который ссылается хотя бы один пресет, удалить нельзя.

## Пресеты и systemprompt

Пресет хранит только постоянные данные: personprompt и массив `module_id`.
Systemprompt собирается в оперативной памяти перед циклом:

```text
personprompt пресета
        +
общее описание .jarvis/environment.txt
        +
актуальные модальности общей модели
        +
актуальный JSON-каталог actions и events модулей
```

Файлы читаются заново на безопасной границе цикла. Добавление module_id в
`modules.json` сразу влияет на широковещательную подписку, а в model contract
попадает со следующего запроса.

Пресет `main` помечен `{"protected": true}` и защищён от создания, замены и
удаления через API. В него можно
только добавить модуль действием `module_manager.add_to_preset`; действия
удаления модуля из пресета нет.

Main не имеет специального цикла или фиксированного ID. Приложение создаёт его
первым с `name="main"` и `preset="main"`. Остальные экземпляры создаются через
`agents.spawn` с указанными родителем name и preset.

## Стандартные модули

### agents

Создаёт, останавливает и перечисляет экземпляры, передаёт адресные сообщения и
управляет файловыми пресетами. Каждая операция публикует
`agents.operation_result` вызвавшему агенту.

### module_manager

Предоставляет рабочую область `.jarvis/modules`, запуск проверок, валидацию,
горячее применение и добавление module_id в пресет. Его personprompt требует
рабочих тестов перед сообщением родителю о готовности. Экземпляр создаётся main
по необходимости из preset `module_manager`.

### speech_input

Handler запускает микрофон, silero-vad и faster-whisper. Завершённая реплика
публикуется как `speech_input.speech` всем агентам с этим модулем.

### speech_output

Handler управляет Fish Audio, а `speech_output.speak` синтезирует реплику.
Событие `speech_output.result` адресуется только вызвавшему агенту.

### system

`system.shutdown` инициирует штатное завершение процесса. Будущая долговременная
память сможет подключиться к этому сценарию, но сейчас не реализована.

## Текущие границы

Контексты живых экземпляров существуют только в памяти и исчезают после
завершения процесса. Автозапуск вместе с ОС и долговременная память находятся
вне текущего этапа.
