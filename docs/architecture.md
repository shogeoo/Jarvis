# Архитектура Jarvis

## Слои

```text
jarvis/core/             неизменяемый event/action runtime
jarvis/modules/          SDK, loader и isolated worker
jarvis/presets/          стартовые конфигурации экземпляров
jarvis/infrastructure/   LLM-конфигурация и диагностика
jarvis/application.py    composition root

.jarvis/environment.txt
.jarvis/modules/<module_id>/
.jarvis/presets/<preset>/
.jarvis/runtime/
```

Ядро резервирует `no_action`, `structure_error` и `module_error`. Все остальные
actions и events приходят из динамически загруженных деклараций.

## Цикл агента

Каждый экземпляр имеет ID (`main` у корневого, случайный `agent-XXX` у остальных), name, preset, собственные
контекст, FIFO, поток и `enabled_modules` в RAM.

```text
накопленная пачка events
        ↓
отдельный user message для каждого event
        ↓
один structured запрос к модели
        ↓
проверка полного JSON-ответа
        ↓
последовательная передача actions диспетчерам
        ↓
агент свободен; фоновые операции продолжаются независимо
```

Последовательность относится к передаче задач. Ядро не ждёт фактического
завершения уборки, синтеза речи, HTTP-запроса или другой работы. Модульный
handler позже превращает результат в обычный event.

Если передача одного action аварийно завершилась, следующие actions всё равно
передаются. Main получает `module_error` с `module_id` и текстом исключения.

## Structure error

Невалидный JSON, неизвестный action, неправильная JSON Schema аргументов и
сочетание `no_action` с другими actions создают `structure_error`. Ошибочный
assistant message сохраняется. Агент остаётся занят, а внешняя FIFO не
добавляется в контекст, пока модель не вернёт корректную структуру.

## Action и handler

Action — короткий dispatcher. Ядро передаёт его отдельному модульному потоку,
который вызывает обработчик `action(data, ActionContext)`. Стандартный action
использует `ActionQueue.submit` и сразу возвращается. Исключение —
fire-and-forget запуск внешней shell-команды (`screenshots.capture` запускает
`hyprshot` через double-fork без ожидания, таймаутов и проверки кода возврата):
handler позже независимо обнаруживает результат во внешней среде.

`ActionTask` хранит внутренние `agent_id`, `action_id`, `action_type` и `data`.
Эти поля нужны маршрутизации и не обязаны показываться модели.

Только handler публикует events. Он может:

- наблюдать внешний источник и рассылать событие всем экземплярам с модулем;
- обрабатывать ActionQueue и отправлять результат конкретному `agent_id`;
- через несколько часов сообщить о завершении ранее принятой операции.

Если handler отсутствует, model-visible обратной связи нет.

## Маршрутизация

`ModuleContext.emit(..., target=None)` рассылает событие всем живым экземплярам,
у которых сейчас включён `module_id`. `target=agent_id` создаёт адресное событие.

Handler внешнего Telegram-поллинга использует broadcast. Handler результата
`send_message` использует agent_id из соответствующего ActionTask.

## Состояние модулей экземпляра

Preset содержит `modules.json`, но этот файл используется только при создании
экземпляра. После запуска каждый агент владеет независимым множеством
`enabled_modules` в оперативной памяти.

Включение модуля одному экземпляру:

1. Loader проверяет и загружает код, если он ещё не загружен.
2. Module_id добавляется только в RAM выбранного агента.
3. Handler запускается один раз глобально.
4. На следующем модельном цикле system message этого агента получает контракт.

Выключение удаляет module_id только у выбранного экземпляра. Когда модуль больше
не включён ни у кого, loader очищает его registry, очередь, handlers, потоки,
процесс и импортированный Python-код.

Preset на диске не меняется. При следующем запуске экземпляр восстанавливается из
памяти вместе со своим сохранённым набором `enabled_modules`; если памяти нет,
используется стартовый набор preset.

## Редактирование module_manager

Module manager работает прямо с `.jarvis/modules/<module_id>`.

Для изменения существующего модуля:

1. Запоминаются живые экземпляры, использующие module_id.
2. Module_id удаляется у них из RAM.
3. Runtime модуля полностью выгружается.
4. Код редактируется в том же каталоге.
5. Выполняются validation и рабочие тесты.
6. Код включается заново.
7. Module_id возвращается сохранённым живым экземплярам.

Агенты и их контексты не перезапускаются. Уже сформированный модельный запрос
невозможно изменить задним числом; следующий цикл строится без выключенного
контракта.

Для нового модуля сохранённых экземпляров нет. После проверки родитель указывает
конкретный живой agent_id, которому module_manager включает новую возможность.

## Каталог для main

Модуль `module_control` даёт текущему экземпляру:

- `list_existing` — каталоги на диске и состояние загрузки;
- `list_active` — собственный RAM-набор;
- `enable` — добавить существующий module_id только себе;
- `disable` — убрать module_id только у себя.

Это позволяет main увидеть существующую интеграцию и подключить её без изменения
preset и без запуска module_manager.

## Декларация и JSON-каталог

`module.py` возвращает `Module(actions=..., handlers=...)`. Каждый handler
перечисляет все events, которые способен опубликовать. Action/event содержат
подробное description и строгую `data_schema`.

Перед запросом к модели prompt builder группирует эти декларации по module_id:

```json
{
  "core_protocol": {
    "actions": [],
    "events": []
  },
  "modules": [
    {
      "module_id": "telegram",
      "description": "...",
      "actions": [],
      "events": []
    }
  ]
}
```

Это единственное описание конкретных возможностей для обычного агента.
Personprompt задаёт личность, а environment — общий протокол без перечня
установленных модулей.

## Зависимости и процессы

Manifest поддерживает два режима.

`in_process` предназначен для доверенного кода без конфликтующих зависимостей.
Он импортируется в процесс Jarvis и может получать внутренние менеджеры через
ModuleContext.

`isolated` предназначен для обычных интеграций:

```json
{
  "execution": "isolated",
  "requirements": "requirements.txt"
}
```

Внутри каталога создаётся отдельная `.venv`. Версии сторонних пакетов должны
быть закреплены через `==`. Worker запускается Python этого окружения. Основной
процесс получает описание, отправляет actions и принимает events по JSON Lines.
Зависимости worker никогда не добавляются в `sys.path` Jarvis.

Неожиданный выход worker создаёт `module_error` для main. Выключение отправляет
shutdown, затем при необходимости завершает всю принадлежащую worker группу
процессов.

## Стандартные модули

- `agents` — экземпляры, сообщения и файловые presets;
- `module_control` — просмотр и RAM-доступ текущего экземпляра;
- `module_manager` — редактирование, тестирование и глобальная выгрузка кода;
- `speech_input` — входная речь, только handler;
- `speech_output` — action постановки речи и handler результата;
- `screenshots` — action `screenshots.capture` запускает hyprshot fire-and-forget,
  handler публикует broadcast-событие `screenshot` (`data.text` — имя файла)
  с отдельной image-частью, base64 в `data` нет.

## Долговременная память

`jarvis/infrastructure/context.py` (`MemoryStore`) хранит по одному файлу
`.jarvis/memory/<agent_id>.json` на экземпляр агента. Запись содержит `agent_id`,
`name`, `preset`, `parent_id`, сохранённый набор `modules` и историю сообщений
без system message.

```text
agent: event / assistant / module change
        ↓
история + метаданные
        ↓
атомарная запись .jarvis/memory/<agent_id>.json
```

`AgentManager.restore` читает все записи, поднимает `main`, затем восстанавливает
субагентов в порядке «родитель раньше ребёнка» с прежними `agent_id`, preset,
модулями и контекстом. Записи с отсутствующим родителем пропускаются и удаляются.
Битые файлы игнорируются. `delete` агента удаляет его файл. Каталог в `.gitignore`;
пока файлы не удалены, контекст переживает перезапуск.

Отдельного `system` нет. Ctrl+C сейчас напрямую запускает очистку runtime.
Автозапуск вместе с ОС находится вне текущего этапа.
