# Jarvis

Личный цифровой ассистент Georgiy Shonichev. Ядро находится в разработке.

Параметры API в `.env`: `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_API_MODEL` и
необязательный `LLM_REASONING_EFFORT` (пусто — дефолт провайдера).
Для режима подписки задай `CHATGPT_SUBSCRIPTION_ENABLED=true`,
`LLM_SUBSCRIPTION_MODEL` и `LLM_API_MODEL`: первая модель работает через вход
ChatGPT OAuth, вторая — через API при исчерпании лимита. Прежний `LLM_MODEL`
пока принимается как имя API-модели. При первом запуске вход ChatGPT
откроется в браузере до события `system_started`.
Подписка использует собственный цикл Jarvis и прямой Responses-транспорт
с ChatGPT OAuth; Codex как агентный runtime не запускается. Входные модальности
подписки: `text` и `image`. Остальные вложения сохраняются в памяти Jarvis,
но не передаются подписному маршруту нативно. Если лимит подписки достигнут,
тот же запрос передаётся настроенному API с его моделью и модальностями.
Состояние входа Jarvis хранится в `.jarvis/runtime/auth/chatgpt.json`, отдельно
от Codex CLI и вне Git.
Для такого переключения API-ключ и модель должны быть настроены заранее.
Остальные настройки заданы в коде. Хранилище — `.jarvis` в корне проекта.
Все модели речи находятся в `.jarvis/runtime/models/`.
STT и TTS настроены на CUDA без CPU fallback; VAD работает на CPU.
Для TTS используется установленный бинарник `s2`.

Запуск: `python -m jarvis`.
Тесты: `python -m unittest discover -s tests`.

В консольной трассе main выделен зелёным, каждый субагент получает случайный
индивидуальный RGB-цвет на весь запуск; ошибки выделены красным. При выводе
в файл цветовые escape-последовательности не добавляются.

System динамически собирается из закрытых XML-блоков в порядке:
`ENVIRONMENT`, `PERSON`, непустой `ADDITIONAL_INSTRUCTIONS`, `MEMORY`
каждого экземпляра, `MODEL_INFO`, `AGENT_INFO`, `CAPABILITIES`.
System не сохраняется в истории.

Пресет — живая обязательная основа всех своих экземпляров:
`presets/<preset_id>/person.txt` и `preset.json` с полями
`description`, `model` (null наследует дефолт из .env) и `capabilities` (единый массив ID).
Изменения PERSON, модели и назначений видны существующим экземплярам при
следующем inference без очистки истории. Assets восстанавливают только
отсутствующие файлы и не заменяют пользовательский PERSON.

Экземпляр сохраняет `agent_id`, `preset_id`, `parent_id`, `model` override,
необязательное `description`, `additional_instructions`, `capabilities_add`. Назначенные capabilities —
объединение текущего пресета и индивидуальных дополнений. Нельзя локально
снять обязательную capability пресета; собственные дополнения независимы.
При создании ядро выдаёт agent_id; имя не является аргументом или техническим
полем. Задача передаётся отдельным сообщением, не через постоянные инструкции.

Main по умолчанию имеет неделимый системный модуль `agents`. Его можно назначить
другому агенту для полного цикла делегирования. `agents.get` возвращает конкретный
экземпляр: person, description, additional_instructions, model и один массив
capabilities, без вложенного effective. `agents.edit` меняет дополнения;
`agents.get_preset` читает полный пресет, `agents.edit_preset` применяет частичный
changes. `agents.list_presets` возвращает только id и description каждого пресета,
без личности и назначений. Описание экземпляра независимо от описания пресета,
не является инструкцией и по умолчанию равно null.
Удаление экземпляра рекурсивно останавливает его дерево. История, файлы и отметка
об удалении сохраняются до архивации сессии; удалённые экземпляры не восстанавливаются.
Удаление пресета делает то же для его экземпляров и потомков. Завершённые архивы сохраняются.
Каждый агент, даже без назначений, имеет `send_message_to_agent`, событие
`message_from_agent` и `no_action`.

Пользовательские capabilities находятся в
`.jarvis/capabilities/{actions,handlers,modules}/<capability_id>/`.
Самостоятельные IDs — snake_case и уникальны между категориями и встроенными
единицами. Публичные операции поиска и назначения принимают `capability_id`,
без отдельного kind. Модуль назначается целиком; его действия вызываются
через `module.action`. Модель получает события, а не описания handlers.
Каталог содержит `actions`, `events`, `modules`; модульные действия и события
не дублируются вне модуля. Новые назначения добавляются в конец каталога.

Встроенный пресет `capability_manager` предназначен только для разработки
capabilities. Контракт разработки находится в description модуля, а не в PERSON или ENVIRONMENT.
Его фиксированные системные инструменты не записываются в назначения пресета.
Только ему доступны `list_capabilities` (все существующие capabilities) и
`toggle_capability` (глобальная пауза). Main их не получает; его
`list_assigned_capabilities` включает системные и приостановленные назначения,
а `list_available_capabilities` показывает неназначенные пользовательские возможности.
Эти списки возвращают один массив capabilities с id и description, без kind;
полные контракты доступны через capability_info. Системные capabilities входят
в общий каталог и механизм вызовов, но отключить, приостановить или удалить их нельзя.
Четыре инструмента входят в системный модуль `capability_development`:
`capability_development.read_file`, `.write_file`, `.edit_file`,
`.execute_command`. Относительные пути и bash без cwd используют
`.jarvis/capabilities/`, без sandbox и без усечения вывода.
Standalone-версии могут использовать тот же SDK-контракт с базой `Path.home()`.
Обе версии одинаково поддерживают текст и мультимодальные вложения.
Каждый execute_command запускает отдельный bash: cd и переменные не переносятся
между вызовами. Нет таймаута результата. Окружения и зависимости capability
организует её собственный код; ядро не читает .env, не выбирает .venv и не
устанавливает requirements.

Глобальная пауза пользовательской capability останавливает её runtime для всех,
не снимая назначений. Локальное снятие индивидуального назначения возвращает
capability в available. Встроенные возможности не подчиняются глобальной паузе
или локальному отключению. Reload: pause → дождаться call_result → изменить и
проверить код → resume отдельным вызовом.

Модель выбирается по цепочке: override экземпляра → модель пресета → дефолт
JARVIS из .env. Недоступная модель вызывает переход к следующему уровню без
перезаписи override. OpenRouter использует provider/model_id, подписка — ID
модели. Ошибка всей цепочки отображается, агент остаётся работоспособным.

J.A.R.V.I.S. — одна система с постоянными когнитивными процессами. Логическая
сессия заканчивается только действием `shutdown`, доступным Main. Ctrl+C или
авария процесса оставляют сессию открытой; перезапуск восстанавливает экземпляры
и их активные контексты. Входы сохраняются при приёме, ответы — перед исполнением.
Доступные рассуждения провайдера сохраняются в истории вместе с сообщениями.

При первом запуске новой логической сессии только Main получает `system_started`.
При повторном запуске процесса в той же незавершённой сессии только Main получает
`system_restarted`. Метка запуска хранится в memory/state.json, независимо от runtime;
сохранившиеся экземпляры с пустыми контекстами после завершения не превращают новую
сессию в перезапуск. Смысл событий описан в их description, не в ENVIRONMENT/PERSON.
При возобновлении незавершённой архивации обычная генерация остаётся замороженной:
уведомление о перезапуске передаётся Main в заключительной служебной фазе,
не изменяя архивируемую историю или уже готовый архив.

Живое состояние находится в `.jarvis/memory/instances/<agent_id>/`:
`instance.json`, `semantic.json`, `context.json`, `files/`, служебный `files.json`.
Каждый экземпляр имеет собственную семантическую память и модуль
`semantic_memory.write/edit/delete`; блок MEMORY обновляется при следующем inference.
Пресеты, идентичность, иерархия и знания сохраняются между сессиями.

Бинарные вложения физически сохраняются под исходными именами (`report.pdf`,
`report_1.pdf`). В context[] находятся `type`, `file_id`, `filename`,
`text_representation` и необходимые сведения формата. File IDs начинаются заново
для каждого экземпляра в каждой сессии. Журнал записи восстанавливает целую
подготовленную пару instance/context после сбоя; JSON и контрольные точки записываются
через fsync и атомарную замену.

Перед архивацией ядро программно преобразует документы в Markdown через готовые
библиотеки [MarkItDown](https://github.com/microsoft/markitdown)/Mammoth, python-pptx, openpyxl и PyMuPDF. DOCX, PPTX, PDF,
XLSX и HTML сохраняют позиции извлечённых медиа, исходные вложения и технические
ссылки на их оригиналы. XML, CSV, JSON, текст и другие поддерживаемые MarkItDown
форматы конвертируются программно. Неподдерживаемый или повреждённый файл
останавливает завершение с ошибкой; данные не отбрасываются молча.

Четыре независимые модели памяти задаются исключительно в `.env`:

```dotenv
MEMORY_MODEL_TEXT=provider/model
MEMORY_MODEL_TEXT_IMAGE=provider/model
MEMORY_MODEL_TEXT_IMAGE_VIDEO=provider/model
MEMORY_MODEL_TEXT_IMAGE_AUDIO_VIDEO=provider/model
```

Укажите действительные идентификаторы вашего API-провайдера; значения выше —
обозначение формата, не готовые модели. Профили поддерживают соответственно текст;
текст и изображения; текст, изображения и видео без аудио; все четыре модальности.
Для аудио используется последний профиль. Наличие аудиодорожки видео проверяет
`ffprobe` из ffmpeg. Ядро выбирает минимальный подходящий профиль. Интерпретации и
индивидуальные изложения используют эти модели, общее изложение — TEXT.
Четыре `MEMORY_MODEL_*` — исключительно API-профили. Они никогда не используются
как идентификаторы моделей подписки. Для подписки задаётся одна независимая настройка:

```dotenv
MEMORY_SUBSCRIPTION_MODEL=subscription-model-id
```

Эта модель используется только при включённом режиме подписки и только для текста
и изображений. Если она не задана, недоступна или исчерпан лимит, ядро обращается
к подходящему API-профилю из четырёх переменных выше. Аудио и видео сразу идут в API
с оригинальными вложениями. Успешная работа через подписку не требует заполненного
API-профиля; если понадобится переход в API, отсутствие нужной настройки остановит
этап с понятной ошибкой. Модель агента ни в один из этих параметров не подставляется.


Архивы завершённых сессий:
`.jarvis/memory/sessions/<session_id>/summary.md` и
`instances/<agent_id>/{context.json,summary.md,files/}`. Служебные метаданные
сохраняют исторический пресет, родителя, описание и реестр оригиналов.
Архив появляется атомарно после всех интерпретаций и изложений. До этого
рабочие контрольные точки находятся вне sessions; живые данные остаются в instances.
При ошибке ядро печатает её в консоль и остаётся замороженным. Остановите процесс
и запустите снова: незавершённый этап продолжится, готовые интерпретации и изложения
не запрашиваются повторно. `memory/state.json` хранит идентификатор и этап сессии.

После фиксации архива ядро очищает контексты и текущие вложения, сохраняя настройки
и семантическую память. Main получает служебный `call_result` completed и одну
возможность произнести заключительный `speech`, иначе `reply`. Это отдельная
служебная фаза: подтверждение, ответ и его результат не попадают в архив. Любое
другое действие не выполняется; затем Python-процесс завершается. После аварии
в заключительной фазе прощание не воспроизводится повторно.

`memory_manager` — обычный системный пресет исследователя опыта, аналогичный
`capability_manager`. Экземпляры создаются через agents, общаются обычными
send_message_to_agent/message_from_agent. Ему назначен неделимый модуль `memory`:
`search`, `list_sessions`, `get_summary`, `get_context_info`, `search_in_context`,
`get_context`, `get_file`. Он может получать agents для исследовательских процессов.
Модуль memory можно назначить другим экземплярам целиком. Его интерфейс только
читает завершённые архивы; незавершённая текущая сессия в поиск не входит.

Поиск использует локальный `Qwen/Qwen3-Reranker-0.6B` на CUDA, независимо от
моделей агентов и API памяти. Веса лежат в
`.jarvis/runtime/models/Qwen3-Reranker-0.6B/`. Для восстановления всех удалённых моделей:

```bash
.venv/bin/python scripts/install_models.py --force
```

Скрипт готовит Whisper large-v3-turbo, Silero VAD, S2 Pro Q4_K_M с токенизатором
и Qwen3-Reranker-0.6B. Все четыре модели устанавливаются независимо от включённых
функций и наличия s2. Загрузка не запускает ассистента и не вызывает платные модели.
`--force` получает свежие файлы, не доверяя прежним копиям и кэшу; обычный повторный
запуск продолжает незавершённые загрузки и пропускает проверенные установки.
Перед публикацией проверяются формат файлов и контрольные суммы Hub, после установки
сохраняется SHA-256-манифест. Неполный набор файлов не считается готовой моделью.
Локальная проверка без скачивания:

```bash
.venv/bin/python scripts/install_models.py --check
```

Команда `python -m jarvis --download-models` использует ту же подготовку всех моделей.
Голосовой референс входит в пакет, производный профиль голоса при необходимости
пересоздаётся речевым сервисом; бинарник s2 устанавливается отдельно.
Отсутствующие или повреждённые веса распознавания и ранжирования также подготавливаются
при их первом использовании. Модель загружается лениво
и совместно используется запросами, оценивая каждую пару запрос/кандидат независимо.
Небольшие пакеты ограничиваются длиной входа; все архивы обходятся последовательно,
без предварительного отсеивания. CPU fallback и старого лимита 8192 MiB нет.

Поиск по контексту формирует около 30 окон по токенам с перекрытием около 15%,
предпочитая границы сообщений. У короткой истории окон меньше, у очень длинной
их может быть больше из-за окна модели. Thinking исключено только из поиска.
Возвращаются включительные индексы исходных сообщений; длинное сообщение может
попасть в несколько окон. get_context включает доступное thinking и интерпретации
в компактных парных маркерах, skip_first/skip_last считаются сообщениями.
Оценки релевантности не являются вероятностью истинности; найденные сообщения
нужно читать и проверять. get_file возвращает исходный файл нативной частью сообщения.

Протокол:
`{"event_id":"event_name","data":{}}`;
`{"actions":[{"action_id":"action_name","call_id":"unique_call","data":{}}]}`;
`{"event_id":"call_result","call_id":"unique_call","data":{}}`.
call_id уникален за весь контекст, включая отклонённые ответы.
Действия выполняются независимо и асинхронно; один вызов имеет максимум один
финальный результат. Ошибки адресуются caller. Interrupt отменяет генерацию,
но сохраняет очередь, историю и уже выполняющиеся actions.
При перебивании озвучка останавливается сразу. Результат speech со статусом
interrupted доставляется после распознавания пользовательской реплики в одной
пачке с speech_detected, перед новым текстом; отдельного inference на самом
старте перебивания нет. VAD и STT продолжают обычное выделение и распознавание речи.

Descriptions настраиваются в `jarvis/assets/capability_descriptions.json`:
массивы `actions`, `handlers`, `modules` содержат только description-поля;
схемы и код остаются в Python. Текстовые шаблоны секций — в `jarvis/assets/`.
В description модуля разработки динамически подставляется `{storage_root}`.
ENVIRONMENT описывает только общую среду и протокол, PERSON — личность и специализацию.
Описания конкретных действий, capabilities, событий, их идентификаторы и инструкции
использования находятся только в description актуального каталога.
