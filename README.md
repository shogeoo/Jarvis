# Jarvis

Jarvis — модульная event-thinking-action система без tool calling. Каждое
событие передаётся модели отдельным `user` message в строгом JSON, а ответ
содержит строгий массив actions.

Долговременная память и автозапуск вместе с ОС пока не реализованы.

## Структура

```text
jarvis/
  application.py
  cli.py
  core/                 # протокол, агенты, пачки и маршрутизация
  modules/              # публичный SDK, загрузчик и isolated worker
  presets/              # файловые стартовые конфигурации
  infrastructure/       # конфигурация и модельный API

.jarvis/
  environment.txt       # общее техническое описание event/action среды
  modules/              # код подключаемых возможностей
  presets/              # personprompt и начальные modules экземпляров
  runtime/              # логи и временные данные
```

`jarvis/core` не содержит STT, TTS, управления агентами или описаний конкретных
модулей. Эти возможности находятся в `.jarvis/modules`.

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[cuda]'
cp .env.example .env
.venv/bin/jarvis
```

Для STT на CPU используется extra `speech` и `STT_DEVICE=cpu`. Микрофон требует
`parec`, воспроизведение — `ffplay`.

## Event/action цикл

Событие и действие имеют одну оболочку:

```json
{"type":"namespace.name","data":{}}
```

Ответ модели:

```json
{
  "actions": [
    {"type":"speech_output.speak","data":{"text":"Добрый вечер."}}
  ]
}
```

Ядро проверяет весь ответ и по порядку передаёт actions соответствующим
модульным dispatchers. Передача не ждёт результата операции. После передачи
всего массива агент освобождается и может обрабатывать следующую пачку.

Action не публикует события. Он помещает внутренний `ActionTask` в очередь и
возвращается. Фоновый handler выполняет задачу и позднее публикует event успеха,
ошибки или прогресса. Результат через миллисекунду и через два часа является
одинаковым обычным событием.

Если handlers нет, actions работают в одну сторону и модель не получает
обратной связи.

`no_action` является единственным встроенным action и не может сочетаться с
другими actions. Неправильный JSON вызывает `structure_error`; внешняя пачка
ждёт исправления. Необработанное падение кода создаёт для main:

```json
{
  "type":"module_error",
  "data":{"module_id":"telegram","error":"текст ошибки"}
}
```

## Пачки

Пока модель думает и ядро передаёт её actions исполнителям, новые события
накапливаются в FIFO. После освобождения агента каждое событие добавляется в
контекст отдельным сообщением в фактическом порядке возникновения.

При `structure_error` ошибочный assistant message остаётся в истории. Модель
видит только описание ошибки и исправляет ответ; остальные события продолжают
ждать в очереди.

## Экземпляры и enabled-модули

Каждый агент имеет собственные ID `agent-000`–`agent-999`, имя, контекст,
очередь, поток и набор включённых модулей в оперативной памяти.

`modules.json` пресета задаёт только начальный набор нового экземпляра.
Включение или выключение во время работы изменяет один экземпляр и не записывает
пресет на диск. Два агента одного preset могут иметь разные возможности.

Main получает через модуль `module_control`:

- список всех каталогов модулей на диске;
- свой текущий активный список;
- включение существующего модуля себе;
- выключение модуля у себя.

## Создание и редактирование

Module manager работает прямо в `.jarvis/modules`.

При редактировании он сначала глобально выключает модуль: runtime, handlers,
очереди и workers очищаются из RAM всех экземпляров, файлы остаются. После
редактирования и тестов он включает код заново, и доступ возвращается живым
экземплярам, у которых был до выключения.

Новый каталог изначально не загружается. После реализации module_manager
проверяет и включает его, затем отдельной операцией назначает конкретному
`agent_id`. Presets при этом не меняются.

## Формат модуля

```text
.jarvis/modules/telegram/
  module.json
  module.py
  actions/
  handlers/
  requirements.txt
  .venv/
```

Декларации `action(...)`, `event(...)` и их подробные описания со строгими JSON
Schema находятся в `module.py`. Загрузчик строит из них JSON-каталог system
message. Без этого каталога модель не знает о существовании возможностей.

Events объявляются только через `event_handler(..., events=...)`.

## Изоляция зависимостей

Модуль со сторонними пакетами объявляет:

```json
{
  "module_id": "telegram",
  "description": "...",
  "entrypoint": "module.py",
  "factory": "create_module",
  "execution": "isolated",
  "requirements": "requirements.txt"
}
```

Module manager создаёт `.venv` внутри каталога и устанавливает версии,
закреплённые через `==`. Worker запускается Python этого окружения и общается с
ядром по JSON Lines. Его `site-packages` никогда не добавляется в основной
процесс.

Доверенные встроенные модули без сторонних конфликтующих зависимостей могут
использовать `execution: in_process`.

## System message

Перед каждым новым циклом первое system message пересобирается в памяти из:

1. `personprompt.txt` экземпляра;
2. `.jarvis/environment.txt`;
3. актуальных модальностей модели;
4. JSON-каталога только включённых у этого экземпляра модулей.

Personprompt и общее описание среды не перечисляют конкретные модули. Все
сведения об их использовании поступают из JSON-каталога.
