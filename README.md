# Jarvis

Jarvis — event-thinking-action система без tool calling. Каждое событие
передаётся модели отдельным `user` message в строгом JSON, а ответ содержит
строгий массив actions с выбранными моделью `action_id`. Каждое действие
возвращает обязательный `ActionResult`, связанный с ним через `action_id`.

Долговременная память реализована: контекст каждого экземпляра агента
сохраняется в `.jarvis/memory/` и восстанавливается при следующем запуске, пока
файлы не удалены. Автозапуск вместе с ОС пока не реализован.

## Структура

```text
jarvis/
  application.py
  cli.py
  core/                 # протокол, агенты, пачки и маршрутизация
  capabilities/         # публичный SDK, загрузчик и isolated worker
  presets/              # файловые стартовые конфигурации
  infrastructure/       # конфигурация и модельный API

.jarvis/                # отдельный git-репозиторий runtime-данных
  environment.txt       # общее техническое описание event/action среды
  actions/              # простые действия: один .py файл — одно действие
  handlers/             # простые handlers: один .py файл — один handler
  modules/              # сложные системы: module_id как контейнер общих зависимостей
  presets/              # personprompt и стартовые capabilities экземпляров
  runtime/              # логи и временные данные
  memory/               # долговременные контексты экземпляров агентов
```

`jarvis/core` не содержит STT, TTS, управления агентами или описаний конкретных
возможностей. Эти возможности находятся в `.jarvis/`.

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[cuda]'
cp .env.example .env
.venv/bin/jarvis
```

Для STT на CPU используется extra `speech` и `STT_DEVICE=cpu`. Микрофон требует
`parec`, воспроизведение — `ffplay`.

## Event/action цикл

Событие, действие и результат имеют одну оболочку `type`/`data`:

```json
{"type":"namespace.name","data":{}}
```

Ответ модели:

```json
{
  "actions": [
    {"action_id":"say-1","type":"say","data":{"text":"Добрый вечер."}}
  ]
}
```

`action_id` придумывает модель; повтор в одном ответе — `structure_error`.

Ядро проверяет весь ответ и по порядку передаёт actions соответствующим
исполнителям. Передача не ждёт результата операции. После передачи всего
массива агент освобождается и может обрабатывать следующую пачку.

Каждое действие обязано вернуть ровно один результат вида:

```json
{
  "type":"action_result",
  "action_id":"say-1",
  "data":{"spoken":true}
}
```

Формат `data` результата задаёт автор действия. Результат возвращается только
инициировавшему агенту и может прийти позже. Результат выполнения команды
не является событием внешнего мира.

Action не публикует события. Падение действия не вешает поток, но и не создаёт
автоматического результата: результат обязано вернуть само действие.
Исключение — fire-and-forget запуск внешней shell-команды (`screenshots.capture`
запускает `hyprshot` через double-fork и сразу возвращает подтверждение):
handler независимо обнаруживает результат во внешней среде и публикует событие.

Снимок экрана — broadcast-событие `screenshot` (`data.text` — только имя файла); PNG идёт
отдельной `image_url`-частью того же OpenAI message, base64 в `data` нет.

`no_action` является единственным встроенным action и не может сочетаться с
другими actions. Неправильный JSON, повтор `action_id` вызывают `structure_error`;
внешняя пачка ждёт исправления. Необработанное падение кода создаёт для main:

```json
{
  "type":"module_error",
  "data":{"module_id":"telegram","error":"текст ошибки"}
}
```

## Пачки

Пока модель думает и ядро передаёт её actions исполнителям, новые события
накапливаются в FIFO. После освобождения агента каждое событие добавляется в
контекст отдельным сообщением в фактическом порядке возникновения.

При `structure_error` ошибочный assistant message остаётся в истории. Модель
видит только описание ошибки и исправляет ответ; остальные события продолжают
ждать в очереди.

## Экземпляры и capabilities

Каждый агент имеет собственный ID (`main` у корневого, `agent-000`–`agent-999` у остальных), имя, контекст,
очередь, поток и набор включённых capabilities в оперативной памяти.

`capabilities.json` пресета задаёт только стартовый набор нового экземпляра:
модули целиком либо отдельные действия и handlers. Часть модуля включить
нельзя. Включение или выключение во время работы изменяет один экземпляр;
только `main` записывает изменения в свой пресет. Два агента одного preset
могут иметь разные возможности.
Текущий набор capabilities экземпляра сохраняется в память и восстанавливается при
следующем запуске.

## Долговременная память

Каждый экземпляр агента хранится отдельным файлом `.jarvis/memory/<agent_id>.json`
с именем, preset, родителем, набором capabilities и историей сообщений. System message
не сохраняется: он пересобирается при запуске из актуальных capabilities.

Контекст записывается после каждого нового события и каждого ответа модели, а
также при изменении набора capabilities. При старте `main` и все сохранённые
субагенты пересоздаются с прежними идентификаторами и контекстами. Удаление
агента удаляет его файл памяти. Незавершённые действия при остановке просто
удаляются из RAM и на диск не сохраняются. Каталог `.jarvis/memory/` в `.gitignore`.

Main получает через модуль `capability_control`:

- список всех capabilities на диске;
- свой текущий активный список;
- включение существующего модуля, действия или handler себе;
- выключение capability у себя.

## Создание и редактирование

Module manager работает прямо в `.jarvis/`.

При редактировании он сначала глобально выключает capability: runtime, handlers,
очереди и workers очищаются из RAM всех экземпляров, файлы остаются. После
редактирования и тестов он включает код заново, и доступ возвращается живым
экземплярам, у которых был до выключения.

Новый каталог изначально не загружается. После реализации module_manager
проверяет и включает его, затем отдельной операцией назначает конкретному
`agent_id`. Presets при этом не меняются.

## Формат capability

Простые действия и handlers лежат напрямую в `.jarvis/` — один Python-файл
строго на одно действие или один handler. Имя файла задаёт ID:

```text
.jarvis/actions/notify_send.py
.jarvis/handlers/computer_is_on.py
```

Каждый файл описывает JSON-контракт: описание, строгую схему аргументов, а для
действия — обязательную строгую схему результата, и реализует результат хоть
как-то.

Сложные системы лежат в `.jarvis/modules/<module_id>/` — контейнер общих
зависимостей, состояния, SDK, конфигов и отдельного виртуального окружения.
Внутри те же папки `actions/` и `handlers/` с правилом «один файл — одна
единица», а вне их может быть общий код:

```text
.jarvis/modules/telegram/
  module.json
  actions/send_message.py
  handlers/new_message.py
  shared.py
  requirements.txt
  .venv/
```

Действия вызываются как `telegram.send_message`, события приходят как
`telegram.new_message`. Часть модуля включить отдельно нельзя — только модуль
целиком.

Загрузчик строит из деклараций JSON-каталог system message. Без этого каталога
модель не знает о существовании возможностей.

Events объявляются только через `handler_definition(..., events=...)`.

## Изоляция зависимостей

Модуль со сторонними пакетами объявляет:

```json
{
  "module_id": "telegram",
  "description": "...",
  "execution": "isolated",
  "requirements": "requirements.txt"
}
```

Module manager создаёт `.venv` внутри каталога и устанавливает версии,
закреплённые через `==`. Worker запускается Python этого окружения и общается с
ядром по JSON Lines. Его `site-packages` никогда не добавляется в основной
процесс.

Доверенные встроенные модули без сторонних конфликтующих зависимостей могут
использовать `execution: in_process`.

## System message

Перед каждым новым циклом первое system message пересобирается в памяти из:

1. `personprompt.txt` экземпляра;
2. `.jarvis/environment.txt`;
3. актуальных модальностей модели;
4. JSON-каталога только включённых у этого экземпляра capabilities.

Personprompt и общее описание среды не перечисляют конкретные возможности. Все
сведения об их использовании поступают из JSON-каталога.
